## 1. Требования

- Безлимитные слоты с метаданными (GDD §12.1, §14.3).
- Обязательная версия сейва и явные миграции.
- Детерминированное восстановление партии: мастер-сид + состояние + журнал команд.
- Устойчивость к обрыву записи и повреждённому файлу.
- Формат читаемый (JSON) для отладки и модов; допускается сжатие позже.
- Никакой зависимости от Godot-типов.

## 2. Расположение и слоты

```
saves/
├── slot-<id>.json          основной файл слота
├── slot-<id>.json.tmp      временный файл записи
└── autosave.json           автосохранение
```

- `<id>` — стабильный идентификатор слота (например, `01J8...`), не зависящий от имени.
- Имя слота задаёт игрок; оно хранится в метаданных, а не в имени файла.
- Количество слотов не ограничено.
- Перезапись — только с подтверждением в UI.
- Удаление удаляет файл и освобождает слот.

## 3. Конверт сейва

```json
{
  "saveVersion": 1,
  "gameVersion": "0.3.0",
  "contentVersion": 1,
  "createdAtUtc": "2026-11-13T12:00:00.000Z",
  "updatedAtUtc": "2026-11-13T12:30:00.000Z",
  "metadata": {},
  "payload": {}
}
```

| Поле | Тип | Обязательно | Назначение |
|---|---|---|---|
| `saveVersion` | int | да | версия формата сейва, управляет миграцией |
| `gameVersion` | string | да | версия игры, создавшая сейв |
| `contentVersion` | int | да | `schemaVersion` контент-паков |
| `createdAtUtc` | string | да | ISO-8601 UTC |
| `updatedAtUtc` | string | да | ISO-8601 UTC |
| `metadata` | object | да | данные для списка слотов |
| `payload` | object | да | состояние партии |

Неизвестные поля `payload` при загрузке игнорируются только вместе с повышением
`saveVersion` и записью в лог; иначе — ошибка.

## 4. Метаданные

| Поле | Тип | Пример |
|---|---|---|
| `name` | string | «Партия Маршала» |
| `day` | int | 12 |
| `factionId` | string | `core.faction.brass` |
| `heroNameKey` | string | `core.hero.brass.marshal.name` |
| `heroLevel` | int | 4 |
| `difficulty` | string | `normal` (MVP — одна сложность) |
| `playtimeSeconds` | int | 5400 |
| `screenshotAsset` | string? | путь к превью (опционально, не MVP) |

Метаданные не должны требовать загрузки всего `payload` для списка слотов:
UI читает только конверт и `metadata`. Реализация этапа 07 обязана это обеспечить.

## 5. Полезная нагрузка

Минимальный состав:

```json
{
  "masterSeed": 123456789,
  "rngState": { "map": 0, "battle": 0, "loot": 0, "levelup": 0 },
  "calendar": { "day": 12 },
  "players": [],
  "map": {},
  "armies": [],
  "heroes": [],
  "settlements": [],
  "resources": {},
  "effects": [],
  "commandLog": []
}
```

- `masterSeed` и состояние стримов обязательны для детерминизма.
- Состояние RNG сериализуется как 64-битное состояние каждого стрима.
- Аккумулятор прироста (`GrowthAccumulator`) сохраняется целиком:
  `availableUnits` (целые доступные юниты) **и** `stockPerMille` (дробный остаток
  в промилле, всегда `< 1000`). Сохранять только целую часть нельзя: это потеря
  прогресса прироста и расхождение с реплеем.
- `growthPerDayPerMille` и `capUnits` — производные от контента; в сейве достаточно
  ссылки на здание/юнит и сохранённого состояния аккумулятора.
- Порядок элементов в массивах стабилен и не зависит от порядка словаря.
- Доменные ID — строки; индексы UI не сохраняются.
- `payload` не содержит presentation-данных (позиции пикселей, анимации).

Точная схема `payload` фиксируется на этапе 02 вместе с доменом и обновляется здесь
до реализации сейвов на этапе 07.

## 6. Журнал команд и реплей

- Каждая команда имеет тип, параметры, номер хода/дня и порядковый номер.
- Журнал позволяет восстановить бой/день с мастер-сида.
- При загрузке состояние восстанавливается из `payload`, журнал используется для
  проверки и будущих реплеев.
- Ограничение размера: MVP — без обрезки; при необходимости архивировать старые
  команды в отдельный файл (решение этапа 07).
- Команды не содержат путей к файлам и UI-состояния.

## 7. Версии и миграции

1. `saveVersion` увеличивается при несовместимом изменении.
2. Каждая миграция — отдельный класс `ISaveMigration` с `FromVersion`/`ToVersion`.
3. Миграции применяются последовательно: 1→2→3, без пропусков.
4. Перед миграцией создаётся резервная копия `slot-<id>.json.bak`.
5. Отсутствующая миграция — отказ с сообщением и логом `Error`, файл не перезаписывается.
6. После успешной миграции сейв сохраняется в новом формате и логируется.
7. Тесты: round-trip текущей версии, миграция с каждой предыдущей, повреждённый файл.

## 8. Атомарная запись

1. Сериализовать в память.
2. Записать `slot-<id>.json.tmp` и вызвать flush.
3. Проверить размер и валидность JSON.
4. Переименовать `.tmp` в основной файл (атомарно в пределах каталога).
5. При ошибке удалить `.tmp`, оставить предыдущий файл нетронутым.
6. Логировать начало, успех и ошибку с `saveId`.

## 9. Безопасность и устойчивость

- Сейв не исполняет код: только данные.
- Пути в сейве относительные; абсолютные пути запрещены.
- Загрузка проверяет `saveVersion`, `contentVersion` и обязательные поля до применения.
- Повреждённый сейв не должен ронять игру: ошибка в UI + лог.
- Автосохранение выполняется в дневном тике и не блокирует UI дольше допустимого.
- Сейвы не синхронизируются автоматически; облачные слоты — вне MVP.

{

Пример неполный намеренно: схема `payload` будет утверждена вместе с доменом.

## 11. Чек-лист реализации

- [ ] Схема `payload` описана и покрыта тестами.
- [ ] Round-trip save→load без потерь.
- [ ] Миграции 1→N и тест каждой.
- [ ] Безлимитные слоты и метаданные без загрузки `payload`.
- [ ] Атомарная запись и восстановление после сбоя.
- [ ] Автосохранение в дневном тике.
- [ ] Логирование записи/чтения/миграций по LOGGING.md.
- [ ] Повреждённый сейв обрабатывается без краша.
