## 1. Принципы

- Моды — граждане первого класса; DLC неотличимо от мода (GDD §15).
- В MVP моды меняют данные, а не код.
- Мод не может нарушать инварианты проекта: лидерство, целочисленная математика,
  стабильные ID, отсутствие автобоя.
- Ошибка мода не должна ломать core-контент: проблемный пак отключается,
  игра продолжает работу с остальными.
- Мод не получает доступ к файловой системе за пределами своего каталога.
- Технически мод — это такой же контентный пак, как `core`; загрузчик, merge
  и валидатор этапа 03 не различают «core» и «мод». Различается только
  `manifest.id` и позиция в порядке загрузки.

## 2. Структура пака

Пак — каталог с `manifest.json` в корне и теми же подкаталогами, что у core
(см. [docs/CONTENT_SCHEMA.md](CONTENT_SCHEMA.md) §2).

```
mods/
└── my_pack/
    ├── manifest.json
    ├── resources.json        # необязательно
    ├── rules/                # необязательно
    ├── factions/
    ├── units/
    ├── hero_classes/
    ├── heroes/
    ├── abilities/
    ├── spells/
    ├── buildings/
    ├── settlements/
    ├── map_objects/
    ├── localization/
    │   ├── languages.json
    │   ├── ru.json
    │   └── en.json
    └── assets/               # ассеты, не читаются загрузчиком контента
```

- Каталог пака — `lower_snake_case`, совпадает с `manifest.id`.
- Обязателен только `manifest.json`; пустой пак допустим, но бесполезен.
- Набор подкаталогов — тот же, что у core; произвольные каталоги игнорируются.
- Ассеты проходят те же правила лицензий, что и core.

## 3. manifest.json

Единый формат манифеста для core и модов (реализовано на этапе 03).

```json
{
  "schemaVersion": 1,
  "id": "my_pack",
  "version": "1.0.0",
  "gameVersionRange": ">=0.3.0 <0.4.0",
  "dependencies": ["core"],
  "loadOrder": 10
}
```

| Поле | Тип | Обязательно | Правило |
|---|---|---|---|
| `schemaVersion` | int | да | поддерживаемая версия схемы манифеста (`1`) |
| `id` | string | да | `lower_snake_case`, совпадает с именем каталога |
| `version` | string | да | SemVer пака |
| `gameVersionRange` | string | да | диапазон совместимых версий игры |
| `dependencies` | string[] | да | ID паков, которые обязаны загрузиться раньше |
| `loadOrder` | int | да | порядок среди паков с равными зависимостями, ≥ 0 |

Правила:

1. Неизвестное поле в манифесте — **ошибка** чтения, а не предупреждение
   (инвариант «неизвестные поля в JSON — ошибка»).
2. `id` мода не может быть `core`; `core` зарезервирован за базовым паком.
3. `dependencies` содержит `core` для любого мода, использующего core-ID.
4. `loadOrder` меньше `core` (0) не запрещён формально, но не имеет смысла:
   зависимости важнее порядка.
5. Поля `nameKey`, `author`, `descriptionKey`, `contentPacks`, `loadAfter`
   в этапе 03 **не поддерживаются**. Если они появятся, это будет новое
   решение через ADR, а не «молчаливое» расширение манифеста.

## 4. Контент пака

- ID записей обязаны иметь префикс `modId.`, например `my_pack.unit.brass.grenadier`.
- Мод может добавлять новые записи и переопределять существующие core-записи
  (см. §6); переопределение — это тот же стабильный ID в новом паке.
- Локализация мода добавляется к общему словарю по языку; ключи — с префиксом `modId.`.
  При совпадении ключа значение мода переопределяет core-значение.
- Ссылки на core-ID разрешены; ссылки на отсутствующие паки — ошибка валидации.
- Схемы данных — те же, что у core ([docs/CONTENT_SCHEMA.md](CONTENT_SCHEMA.md)).
- Файлы правил `rules/*.json` мода переопределяют правило целиком (last-wins),
  а не сливаются по полям.

## 5. Порядок загрузки

Порядок определяет `ContentMerge.PlanOrder` детерминированно:

1. Топологическая сортировка по `dependencies` (зависимость — раньше зависимого).
2. При равной готовности — меньший `loadOrder`.
3. При равном `loadOrder` — `id` по ординальному (побайтовому) сравнению.

Правила:

1. Циклическая зависимость — ошибка (`CONTENT_DEPENDENCY_CYCLE`); merge не строится.
2. Отсутствующая зависимость — ошибка (`CONTENT_DEPENDENCY_MISSING`).
3. Пустая строка в `dependencies` — ошибка (`CONTENT_DEPENDENCY_EMPTY`).
4. Дубликат `id` пака в наборе — ошибка (`CONTENT_PACK_DUPLICATE`).
5. Порядок фиксируется в сейве: изменение порядка не меняет уже сохранённую партию
   без предупреждения.

Так как порядок полностью детерминирован, одинаковый набор паков всегда даёт
одинаковый реестр — это важно для реплеев и сейвов (ADR-017, ADR-018).

## 6. Конфликты и переопределения

| Ситуация | Поведение этапа 03 |
|---|---|
| Дубликат ID внутри одного пака | ошибка загрузки (`CONTENT_ID_DUPLICATE`) |
| Дубликат ID между паками | last-wins: побеждает пак, загруженный позже; запись в журнал `ContentChange` |
| Мод переопределяет core-ID | разрешено тем же правилом last-wins; переопределение логируется |
| Мод переопределяет правило `rules/*` | разрешено; правило берётся из последнего пака целиком |
| Мод переопределяет язык/ключ локализации | разрешено; таблица языка и ключи сливаются по last-wins |
| Отсутствующая зависимость | ошибка merge, реестр не строится |
| Циклическая зависимость | ошибка merge, реестр не строится |

Важно: этап 03 **не** отклоняет переопределение core-ID. Вместо запрета
каждое переопределение попадает в журнал merge (`ContentChange` с полями
`Kind`, `Category`, `EntityId`, `SourcePack`, `ReplacedPack`) и в лог.
Такой журнал позволяет показать игроку и моддеру, кто и что переопределил.
Если позже понадобится явный флаг `override` или запрет — это новое решение
через ADR, а не тихая смена поведения.

## 7. Ограничения MVP

- Нет скриптов, изменения кода, доступа к сети и файлам вне пака.
- Нет переопределения формул, отменяющих инварианты.
- Нет добавления новых типов эффектов без поддержки в ядре.
- Нет загрузки модов во время боя; список паков фиксируется на старте партии.
- Мод не может включать автобой в игровых режимах.
- Мод не может менять `schemaVersion` core-файлов «на лету»; несовместимая
  версия схемы — ошибка (`CONTENT_SCHEMA_VERSION_UNSUPPORTED`).

## 8. Безопасность

- Data-мод не исполняется: только JSON и ассеты.
- Пути в манифесте нормализуются и не могут выходить за каталог пака (`..` запрещён).
- Прямой файловый IO в `Game.Core` запрещён: чтение идёт через
  `IContentFileSystem`, адаптеры — в presentation-слое (ADR-024).
- Ошибки парсинга не показывают содержимое чужих файлов.
- Скрипт-моды M4 — отдельный ADR, песочница и permissions.

## 9. Скрипт-моды (M4)

- C# через Roslyn, ограниченный API, без прямого доступа к ОС.
- Разрешения запрашиваются манифестом и подтверждаются игроком.
- Детерминизм обязателен: скрипт не использует `System.Random`, время и сеть.
- Песочница и модель угроз — отдельные документы и ADR перед реализацией.

## 10. Логирование

Обязательные записи (категория `Content`):

- загрузка манифеста: `packId`, `version`, `loadOrder`;
- порядок загрузки паков;
- переопределение: `category`, `entityId`, `sourcePack`, `replacedPack`;
- ошибка зависимости: `packId`, `missingDependency`;
- цикл зависимостей: список неразрешённых паков;
- итог merge: число паков, сущностей, языков, переопределений.

Формат — [docs/LOGGING.md](LOGGING.md).
